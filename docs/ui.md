# 桌面 UI 使用说明

React + MUI 的玻璃拟态仪表盘，只经 D-Bus 与 `clevod` 通信，不直接
接触硬件。本文说明界面结构与各项设置。

> 本文以 **Tauri 2** 壳为准。同一套前端也能跑在 **Electron** 壳下（见
> [`electron.md`](electron.md)），界面与功能一致，差别只在窗口/渲染引擎与
> 少数兼容性选项的落地方式。

## 1. 界面结构

```
┌───────────────────────────────────────────────┐
│ 侧栏(240px) │ 自绘标题栏：当前页面 + 窗口按钮       │
│ 概览        │ 概览：硬件占用 / 性能模式             │
│ 风扇        │──────────────────┬───────────────│
│ 设置入口    │ 风扇模式 / 转速历史 │ 风扇曲线        │
└───────────────────────────────────────────────┘
```

- **自绘标题栏**：窗口用 `decorations: false`，标题栏即应用顶栏，可拖拽移动；
  右侧三个按钮为**最小化 / 全屏 / 关闭**。关闭即**回到系统托盘**（进程继续运行），
  退出需经托盘菜单的「退出」或设置中的退出项。
  > 两个壳的落法不同：**Tauri** 是隐藏窗口（WebKit 进程随之销毁）；**Electron**
  > 是销毁窗口以释放 Chromium 渲染进程，重开时重建。见
  > [`electron.md`](electron.md) §6。
- **侧栏**：品牌名、概览 / 风扇两个页面、设置入口。页面采用点击切换，不再使用滚动定位。
- **概览页**：左列依次显示硬件占用、内存与 zram/swap 占用、硬盘挂载占用；右列显示性能模式。
- **风扇页**：左列上方显示风扇模式、下方显示转速历史；右列显示风扇曲线，并跨越两行。
- **卡片**：所有卡片使用统一的玻璃表面、边框、圆角和间距，内容区域保持在设计画布内对齐。

### 1.1 概览页硬件数据

硬件占用由 Rust 后端读取，前端只通过 `get_hardware_usage` 获取结果。数据与风扇快照
一起初始化，并每 2 秒刷新一次。

| 卡片 | 内容 |
|---|---|
| 硬件占用 | CPU / GPU 占用圆环，以及右侧的温度、频率、风扇转速。GPU 驱动没有提供占用率时显示不可用提示。 |
| 内存占用 | 内存占用、zram / swap 占用，使用线性进度条分别显示。 |
| 硬盘占用 | 每个物理磁盘挂载点的使用率，使用线性进度条显示。 |
| 性能模式 | `quiet` / `pwrsaving` / `performance` / `entertainment`，写入仍通过 daemon 的 PolicyKit 授权。 |

硬盘列表只保留 `/dev/` 设备提供的挂载点，排除 `/efi`，顺序固定为 `/`、`/home`、
其他挂载点。挂载点不超过 6 个时单列显示，超过 6 个时切换为双列；后端没有返回
挂载信息时显示对应提示。

### 1.2 风扇页

- **风扇模式**：`auto` / `quiet` / `maxq` / `max` / `customize`。`customize` 在网格中
  单独占满一行。
- **转速历史**：记录 CPU 风扇和 GPU1 风扇的最近 60 个采样点。
- **风扇曲线**：在 `customize` 模式下显示可编辑曲线；其他模式显示切换提示。

风扇页使用固定网格定位，风扇模式和转速历史保持在左列，风扇曲线保持在右列，避免
由于卡片内容高度变化而被网格自动排到页面底部。

### 1.3 风扇曲线编辑

「风扇曲线」卡片**只在风扇模式为 `customize` 时出现**。

风扇模式里的 `customize` 按钮就是固件的 `custom`（值 6）。UI 上叫
`customize`，是因为它是用户用来编辑并应用自有曲线的模式；写入时发送给守护
进程的仍是 `custom`。其他模式下固件根本不使用自定义曲线，卡片会换成一句
提示，不显示可编辑的图表 —— 否则会让人以为拖过的曲线已经生效。

排布上，四个预设（`auto` / `quiet` / `maxq` / `max`）占 2×2 网格，`customize`
**单独占满一整行**，避免被读成第五个预设。

在 `customize` 模式下，卡片可直接编辑：

卡片自上而下分两块，与 `cc30-ui/fan.tsx` 的参考设计对齐：

1. **实时读数**：CPU / GPU1 各一列，显示当前温度与该温度在（草稿）曲线上对应的
   占空比。占空比按相邻两点线性插值，所以它是固件此刻会执行的值，而不是最近点。
   拖动时这一列切换成**被拖点的**（温度，占空比），松手恢复。
2. **图表**：左侧独立的占空比刻度槽，下方温度刻度，图内为 25/50/75 位置的虚线
   网格。曲线是三次贝塞尔（`curvePath`），不是折线，因此没有拐角。

**两根轴的范围不同**：

| 轴 | 范围 | 刻度 |
|---|---|---|
| X（温度） | **按曲线自适应**（本机 40~100°C） | `40/55/70/85/100°C` |
| Y（占空比） | **固定 0~100%** | `0/25/50/75/100%` |

X 轴自适应是因为曲线只存在于首末两点之间：固定 0~100°C 会让左边（40°C 以下）
一直空着、曲线挤在右边。

Y 轴**保持 0~100%** 是因为占空比是绝对量：0% 表示风扇停转，必须看得见；
压缩到 25~100% 会让只有 25~100 的曲线显得比实际更陡。代价是曲线底部会空出
一段，这是刻意的。

CPU 与 GPU1 **共用 X 轴**（取并集），所以两线起点落在同一 x、能直接对比；
某一风扇末端温度稍低（如 GPU1 的 99°C）时，其末点略微内缩，正是它的数值位置。

轴取自 **daemon 的曲线而非草稿**，否则拖动时轴会跟着变，点会从指针下滑走。

图表下面直接是三个按钮。

> 卡片**不重复罗列数据**：既没有四个点的数值表，也没有色块图例 —— 哪条线是哪个风扇
> 由读数区的列名（CPU / GPU1）与线的颜色对应，点值由图和控制点表达，改动与否由图
> 上方的「未应用」标记表示。原始数值仍可在 CLI（`clevo-cc fan get-curve`）与内核
> `fan_curve` 中查看。

交互细节：

- **拖动任一条线的端点**即可调整该点的（温度，占空比）。只有命令 14 携带的
  中间两点可拖，**也只有这两点画控制点**；首末两点属 EC，不画标记（画了会让人
  以为能拖，拖了却什么也不会发生），但曲线仍然连到它们，形状因此完整。
  温度被约束为严格递增，拖过头会顶住相邻点而不是让曲线失效。
- 控制点是 14×14、6px 圆角的方点，带白色描边与投影（对齐参考设计）；拖拽中会被
  放大并显示标签，写明**正在拖哪条线、哪个点**（如 `CPU · 55°C 40%`）—— 两条线
  靠近时不容易分辨。两条线重合时命中的是画在上面的 GPU1。
- 命中判定用的是**屏幕像素**半径（16px）而非曲线单位，因此卡片大小变化时手感一致。
  为此把点的位置换算成"绘图区百分比"，再除以**每百分比多少像素**得到像素距离 ——
  乘反了会让 16px 变成约 120px（绘图区的 17%），整张图处处都能抓到点。
- **卡片内的文字不可选中**（`user-select: none`），且按下时会 `preventDefault`。
  否则从控制点往外拖、指针扫过下方刻度或上方读数时，浏览器会把那当作**原生文字
  选择**：拖动变成"拖选区"，曲线丢掉指针、点不再跟随。
- 编辑是**本地**的：拖动只改界面，「保存配置」才写入 EC —— 一次写入会触发
  一次 PolicyKit 授权，不应每拖一下都弹窗。
- 三个按钮分工明确：
  | 按钮 | 行为 | 是否写硬件 |
  |---|---|---|
  | **保存配置** | 把编辑区的内容写入 EC，并切到 `customize` | ✅ |
  | **还原配置** | 丢弃本地编辑，回到 EC 当前的值 | ❌ |
  | **还原默认** | 把出厂曲线载入编辑区（见 `FACTORY_CURVE`） | ❌ |
- 保存后自动切换到 `customize` 模式（否则固件不会使用新曲线），并**重新从 EC
  读取**曲线显示，避免把"已发送"误当成"已生效"。
- CPU 与 GPU1 各自独立，改一条不会动另一条。
- 只读后端（`acpi_call` / Mock）下不显示编辑控件。
- **草稿不会被轮询冲掉**：采纳 daemon 曲线的前提是「内容确实变了」且「本地没有未
  保存的编辑」。轮询每 2 秒重建一次曲线对象，但内容相同，因此不会覆盖草稿；松手
  也不会（松手曾经会 —— 见下）。
- 若后台有别的客户端改了曲线而用户正在编辑，界面**保留用户的草稿**，不会静默
  丢弃；用户「保存配置」或「还原配置」之后才会采纳外部值。

> **曾经的一个 bug**：拖动端点松手后曲线立刻弹回原值。原因是采纳用的 `useEffect`
> 把 `dragging` 放进了依赖数组，而松手正是 `dragging` 从 `i` 变回 `null` 的时刻，
> 于是 effect 重跑并把草稿重置成 EC 的值。现在改为按**内容**判断是否采纳，与拖动
> 状态无关。回归测试见 `src/components/CurveCard.draft.test.tsx`（用旧逻辑跑会失败）。

## 2. 设置

设置是一个应用内窗口，左侧分区导航，右侧选项面板。

### 2.1 个性化

| 项 | 说明 |
|---|---|
| 主题模式 | 深色 / 浅色玻璃 |
| 自定义壁纸 | 从壁纸提取强调色；可重置 |
| 强调色 | 自定义取色器；影响按钮、图表、曲线、侧栏等全部强调色 |
| 卡片颜色 | 玻璃底色（默认随主题模式） |
| 透明度 | 玻璃表面不透明度（越低越透，模糊越明显） |
| 动画 | 使用开 / 关开关控制页面和设置切换动画 |
| 动画速度 | 50%–200%，默认 100%；数值越高切换越快 |
| 文字颜色 | 界面文字颜色（默认随主题模式） |
| 品牌文字 | 左上角名称与副标题，留空隐藏 |
| 图标 | 替换左上角 logo（默认用内置图标） |

动画开关关闭后，页面切换、设置弹窗、设置页分区切换以及玻璃表面的主题过渡会
直接完成；动画速度仅在动画开启时影响过渡时长。页面内容使用小幅位移动画，不对
整张卡片降低透明度，因此不会导致毛玻璃效果在切换时消失。

### 2.2 显示

| 项 | 说明 |
|---|---|
| 比例 | `16:9` / `16:10`，切换后分辨率列表相应更新 |
| 分辨率 | 按比例的预设列表（见下），决定窗口尺寸 |
| 缩放 | 整个界面的缩放比例，输入 50–200% |

**分辨率预设**（宽度 × 高度）：

- **16:9**：568×320、854×480、1024×576、1280×720、1600×900、1920×1080、
  2560×1440、3840×2160
- **16:10**：1280×800、1440×900、1680×1050、1920×1200、2560×1600、3840×2400

窗口尺寸与缩放会**持久化**，重启后自动恢复（`tauri.conf.json` 中的尺寸仅在
首次启动、尚无记录时生效）。

界面以 **1600 宽为设计基准**，高度随所选比例变化：**16:9 用 1600×900，16:10 用
1600×1000**。布局按该尺寸排版，再整体等比缩放到实际视口
（`min(视口宽/设计宽, 视口高/设计高)`），因此任何窗口尺寸下都不会出现滚动条，
16:10 窗口也能铺满整个窗口而不留黑边。组件内**不使用** MUI 的视口断点
（`xs`/`sm`/`md`/`lg`/`xl`），否则会在缩放后的窗口上错误折叠网格。

### 2.3 兼容性

| 项 | 说明 |
|---|---|
| 显示后端 | `Auto` / `Wayland` / `X11`（`GDK_BACKEND`），下次启动生效 |
| 软件渲染 | 彻底禁用 DMA-BUF 与 GPU 合成（兜底用，会失去模糊） |
| 玻璃模糊 | `Auto` / 开 / 关，立即生效 |
| 模糊度 | 模糊半径 0–40px |

> 启动时**始终**设置 `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1`：NVIDIA 专有驱动下
> WebKitGTK 会因 GBM 缓冲分配失败而崩溃（`Gdk Error 71`），改为共享内存传输即可
> 规避，同时**保留**硬件加速与毛玻璃。详见
> [`hardware-notes.md`](hardware-notes.md) §15。

### 2.4 取色器

强调色 / 卡片色 / 文字色共用一个自绘取色弹窗（不用系统原生取色器，因为
WebKitGTK 不响应对隐藏 `<input type=color>` 的程序化点击，且系统样式与玻璃设计
不符）。弹窗内含：饱和度/明度方块、色相条、十六进制输入、壁纸取色板、RGB 回显。

## 3. 系统托盘

托盘图标（左键）弹出**原生菜单**：

```
性能模式：<当前模式>  ▸
  ▶ 静音
  ・ 节能
  ・ 性能
  ・ 娱乐
─────────────────────
打开控制中心
退出
```

- **性能模式**：直接经 daemon 的 PolicyKit 授权切换，无需打开窗口。
- 当前模式用行首标记表示：**`▶ `** 为当前模式，**`・ `** 为其他模式。两个符号
  等宽，切换时菜单不会左右跳动。切换模式后**重建整个菜单**再 `set_menu`
  （宿主不会刷新仅改标题的子菜单）。
- Linux 的托盘是 AppIndicator，**只支持原生菜单、不向程序发送点击事件**（与
  Windows/macOS 不同），因此不使用自绘弹窗。
- 需要 `libappindicator3` / `libayatana-appindicator3`（见
  [`support-matrix.md`](support-matrix.md) §3.3）。

## 4. 运行与验证

```bash
# 开发（Vite dev server + Tauri）
cd ui && pnpm tauri dev

# 或在桌面会话下经脚本启动（会读取兼容性偏好并注入环境变量）
scripts/run-ui.sh --dev

# 构建发布版
cd ui && pnpm tauri build
```

自测（无需硬件、无需桌面）：

```bash
cd ui && pnpm test          # 前端单元测试
cd ui/src-tauri && cargo test   # UI 后端（prefs/assets/dbus）
```

当前前端测试覆盖 190 项。Electron 版本使用同一套 `ui/src` 前端和
`ui/src-tauri` 无壳后端，修改 UI 后应重新构建 Electron 产物：

```bash
cd ui
pnpm build
./node_modules/.bin/electron-builder --linux dir
```

构建后的 Electron 目录为 `ui/release/linux-unpacked/`。

真实数据需要 `clevod` 运行（`sudo packaging/install.sh --enable`）；没有它时
UI 显示"正在连接 clevod…"，但界面、主题与模糊仍可验证。
